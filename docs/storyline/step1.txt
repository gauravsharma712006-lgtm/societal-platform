# 10. MongoDB Atlas Connection

MongoDB Atlas was configured as the project's database.

The backend contains:

```text
server/src/config/database.ts
```

Its responsibility is to establish the MongoDB connection.

Core logic:

```ts
const mongoUri = process.env.MONGODB_URI;

if (!mongoUri) {
  throw new Error('MONGODB_URI is not defined in environment variables');
}

await mongoose.connect(mongoUri);
```

The server waits for the database connection before starting Express.

This was intentionally designed as:

```text
Start server
     ↓
Connect MongoDB
     ↓
Connection successful?
     ↓
YES
     ↓
Start Express
```

If the database connection fails, the application does not continue running as if everything were normal.

This prevents situations where the API appears to work while database operations are actually unavailable.

# 16. Password Security

One of the most important parts of Progress Step 1 was password security.

The password provided by the frontend is NOT stored directly in MongoDB.

Instead:

```text
User enters password
        ↓
Backend receives password
        ↓
bcrypt.hash(password, 12)
        ↓
Hashed password
        ↓
MongoDB
```

The hashing code is:

```ts
const hashedPassword = await bcrypt.hash(password, 12);
```

The value `12` represents the bcrypt cost factor.

The database should therefore contain something similar to:

```text
$2b$12$................................
```

instead of:

```text
Test@123456
```

This is an important security requirement.

# 19. Duplicate Email Protection

Before creating a user, the backend checks:

```ts
const existingUser = await User.findOne({
  email: email.toLowerCase().trim(),
});
```

If the email already exists:

```http
409 Conflict
```

is returned.

Response:

```json
{
  "status": "error",
  "message": "User with this email already exists"
}
```

This prevents duplicate user registrations.

---

# 20. Email Normalization

Email addresses are normalized using:

```ts
email.toLowerCase().trim()
```

This means:

```text
 Gaurav@Example.com
```

becomes:

```text
gaurav@example.com
```

This helps maintain consistent database values.

# 34. Why This Architecture Was Chosen

The project is intentionally separated into layers.

## Frontend

Responsible for:

* User interface
* User interaction
* Form handling
* Displaying API responses

## Services

Responsible for:

* API communication
* HTTP requests
* Keeping network logic separate from UI

## Routes

Responsible for:

* Mapping HTTP endpoints to controllers

## Controllers

Responsible for:

* Handling HTTP requests
* Returning HTTP responses

## Models

Responsible for:

* Database structure
* MongoDB interaction

## Configuration

Responsible for:

* Database connection
* Environment-specific configuration

This separation will make the project easier to scale.

# 35. Important Development Problems Encountered

Several issues were encountered during setup and successfully resolved.

## Issue 1 — npm PowerShell execution policy

Initially npm commands were blocked because PowerShell prevented execution of:

```text
npm.ps1
```

The execution-policy issue was resolved.

---

## Issue 2 — npm build executed from wrong directory

Initially:

```text
npm run build
```

was executed from the project root.

There was no root package.json for the backend command.

The correct command was executed inside:

```text
server/
```

After that:

```text
npm run build
```

completed successfully.

---

## Issue 3 — Port 5000 already in use

The backend initially encountered:

```text
EADDRINUSE
```

because another process was already using port 5000.

The conflicting process was resolved and the backend subsequently started correctly.

---

## Issue 4 — MongoDB connection verification

There was initially uncertainty about whether the backend process was connected to MongoDB Atlas.

The backend was configured to connect to MongoDB before starting the HTTP server.

After correcting the running process/configuration, the backend successfully reported:

```text
MongoDB connected successfully
```

---

## Issue 5 — Duplicate scripts key in frontend package.json

The frontend package.json temporarily contained two `scripts` properties.

This was identified and corrected so that the package configuration contains a single scripts object.
